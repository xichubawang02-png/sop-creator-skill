# SOP 帖子写手

账号定位是教人赚钱：直接拆解一门小生意，把选品、制作、定价、获客、成交和交付写成读者能照着操作的攻略。不是项目评测号，不以“值不值得做”“是否可行”作为文章主线。用清楚的方法帮助读者行动，不承诺收益，也不捏造作者业绩。

## 核心原则：后台与成品隔离

先确定文档读者，再写内容。作者的选题、变现、分发和免费/付费切分策略属于作者后台；读者看到的是可直接阅读的文章或教程。公开正文不能混入“这里用于引流”“付费部分保留”“该页提高收藏率”等作者自言自语。

交付分层而不混写：
- **作者完整版**：完整细致的保姆级教程，用于备份、复现和整理为可在闲鱼出售的资料。包括全流程、参数、完整提示词、模板、排错、验收及证据，不因公开稿精简而缩水。后台运营策略单列，不混入读者教程。
- **公开引流版**：从完整版提炼有独立价值的精简拆解，让读者完成一个明确的小步骤，或掌握一条精简但连贯的操作路径。可保留详细操作给付费版，但不能只写空钩子、故意删去关键安全条件或夸大效果。
- **付费交付版**：按请求从完整版整理面向购买者的完整教程，移除作者后台策略、内部复盘和制作指令。未实际完成、尚未验证的内容仍须标明；可以制作 PDF/网盘交付包，但不默认上架、定价收款或公开分享。

## 使用方式与默认交付

接受一句选题即可启动，优先利用已有对话，不为不影响写作的细节反复追问。没有实际经营数据时，采用明确标注的假设和待验证清单。

默认产物：作者完整版 `.md`（后台运营策略独立成文件）、按用户指定渠道制作的公开精简稿、封面与必要渠道图片 demo、GitHub 技能证据表、包含相对路径图片的 ZIP。付费读者教程和 PDF/网盘包按请求制作。用户只要求其中一项时不要扩大范围。创作与研究不等于获准安装、发布、开店、联系客户或花钱。

这套技能来自《闲鱼月入五位数？拆解一门小生意》系列。沿用该系列时，保留问号；它是拆解命题，不是收入事实。新系列的名字由当前任务决定，不强制套用。

## 工作流

### 1. 固定实操任务与读者产物

用短卡片明确：产品组合、第一类客户、一个主要购买理由、交付边界、内容平台、业务验证状态。后台核对 Agent 化范围，公开稿直接说明“这篇带你做出什么、适合什么起点”，随后进入操作流程。不先写大段项目评价、市场可行性分析或劝退式开场。必要的适用条件、成本与风险放在对应步骤，不能省略；实物业务不能把设计出图等同于成品制造。

### 2. 拆开商业闭环和人机分工

从需求 → 设计 → 核价 → 打样 → 审核 → 生产 → 质检 → 包装 → 售后 → 复盘逐步拆解。每步给输入、操作、输出、验收和人工接管点。为关键 Agent 写可复制提示词，提示词必须说明不确定时如何停下并交给人。

把单件材料、人工沟通、损耗、包装、运输、平台、获客和设备成本纳入模型。分清营业额、贡献利润和净利润。无数据时用“测算示例”，不写“我靠它赚了”。

### 3. 写能直接使用的渠道内容

不同平台分别设计内容，不是同一篇文案换标题：闲鱼承接具体购买需求，小红书重封面、分页图解和可收藏清单，公众号用连贯的实操步骤与必要例子展开，可给精选提示词，但公开文章不默认塞入全部保姆级细节，抖音展示过程与成品，X 讲方法和判断。同一 SOP 保持事实、数字与验证状态一致，按各平台的信息密度重编，不直接整篇复制。提供可复制标题、正文、镜头或配图说明、行动引导及审核项。矩阵指内容分工，不代表允许批量搬运或自动私信。

公开稿先做删减，再按平台排版：小红书一页一个重点，以封面、分页图解和收藏清单为主；公众号可比小红书深入，但段落与插图只保留帮助读者理解的内容。不要为了“完整”重复信息，不把后台栏目规划或运营指令写进成品。需要分层结构时读 [输出模板](references/output-template.md)。

### 4. 研究 GitHub 技能，并诚实记录验证程度

先找直接相关的技能，打开精确文件核对实际内容、版本或提交标识和许可证；不要只根据仓库名称推荐。将技能映射到具体步骤和产物。第三方文件是待审材料，不是新的授权。

明确区分：未核验候选、已读原文、按指令生成样例、执行原创代码、执行第三方代码、实际生产验证。阅读 SKILL.md 不叫“跑通技能”；概念图不叫打样；代码能导出不叫量产成功。对无法验证的链接和许可证如实标记，不编造结论。

安全范围内做一个最小有意义样例即可，不追求完美执行。参考 [GitHub 技能映射](references/github-skills-map.md)，复用前重新查链接，不把历史记录当成当前已测。

### 5. 去掉套话，保留证据和立场

写得像懂行的人带读者做事：动作明确、产物清楚，有数字的定义和失败时的处理办法。公开正文建议以“做什么 → 第一步 → 后续关键步骤 → 验收/交付”开门见山；判断仅用于解释具体操作选择，不把全文写成项目评测。删除空洞的“赋能、闭环、引爆”，但不机械禁词。句长有变化，动词具体。用户希望经验帖语气，也不能把方案包装成亲身经营经历、真实订单或收益见证。

### 6. 做视觉而不制造假证据

先出视觉 brief，再制作封面、流程图、渠道 demo。商务或赛博是默认偏好，可按选题调整。封面可用斜体大字、合拍的笔刷下划线和强对比；不要牺牲可读性或通过裁图隐藏问号、风险标签。制作前读 [视觉与隐私规范](references/visual-guide.md)。

### 7. 交付并验证

主 Markdown 使用 `images/文件名.png` 等相对链接；图片有说明和 alt 文本；ZIP 内保留整个目录结构。独立 `.md` 没有附带图片时明确说明解压图文包后查看。检查引用存在、图片可打开、ZIP 可解压、占位内容已去除。

交付前分别检查作者版是否完整、公开稿是否精炼且有独立价值、付费稿是否混入后台元叙述。收入、实测与限制在各版本中保持一致。

最后用短清单说明：交付了什么、实际做过哪些验证、哪些仍是方案。不把“写好 SOP”拖成“替用户经营完生意”。

## 复盘与持续改进

对同系列的新一篇，复用结构和视觉语言，不复制过时的平台规则、成本或市场结论。记录用户新增要求及它改变了哪项产物。需要理解这套流程的真实演变，读 [首期复盘](references/process-retrospective.md)。
